# Grounding quotes that span several table rows

Date: 2026-09-28
Feeds: the fix for `table_grounding.quote_is_grounded` wrongly rejecting a verbatim multi-row quote. The
proposed rule under review: accept a verbatim quote only when it contains the claimed cell's complete row
text, from the row label through the cell, plus the group label when one exists.

## Question

1. How do table fact-verification and table-QA evidence systems represent and check cell-level evidence? Does
   any of them use row-contained spans or cell coordinates instead of text matching?
2. What failure modes of text-span matching over linearized tables are known (row splicing, column
   misalignment), and how are they mitigated?
3. Does the proposed "complete own row inside a verbatim quote" rule hold against the splice, cross-group
   steal, wrong-period column and header cherry-pick cases in `tests/test_table_grounding.py`?

## Findings (what the sources say)

1. **Benchmarks record evidence as structure (coordinates or rows), not as quoted text.**
   - **FEVEROUS** addresses cells by coordinates: "A table consists of cells c_{i,j}, where i and j specify the
     row and column". Context is added to cell evidence automatically: "For table cells, we also include the
     nearest row and column headers; if the element just before the nearest row/column is also a header, then
     it will be included in the context." (§3) https://ar5iv.labs.arxiv.org/html/2106.05707
   - FEVEROUS gives credit only when a *complete* gold evidence set is predicted:
     "Score = 1 iff ∃E∈𝔼: E⊆Ê ∧ ŷ=y" (§5.1). Its baseline linearizes each cell as
     "[CONTEXT-HEADER] is [CELL]" (§4). https://ar5iv.labs.arxiv.org/html/2106.05707
   - The FEVEROUS toolkit resolves a table from a cell id (`get_table_from_cell_id`).
     https://raw.githubusercontent.com/Raldir/FEVEROUS/main/README.md
   - **FinQA** uses the whole row as the unit of evidence. `gold_inds` keys are row ids. For example, dev
     example 0 has `{'table_3': 'company the american express of payments volume ( billions ) is 637 ; ...'}`.
     https://raw.githubusercontent.com/czyssrs/FinQA/main/dataset/dev.json (downloaded and inspected)
   - `table_row_to_text` puts the row label and the column header next to every cell:
     `"the " + row[0] + " of " + head + " is " + cell + " ; "`.
     https://github.com/czyssrs/FinQA/blob/main/code/utils/general_utils.py (lines 21-34)
   - **TAT-QA** raw data records only `answer_from` (`table`/`text`/`table-text`), `rel_paragraphs`, `scale` and
     `derivation`, with no cell location.
     https://raw.githubusercontent.com/NExTplusplus/TAT-QA/master/dataset_raw/tatqa_dataset_dev.json
   - The TagOp preprocessing adds `mapping: {'table': [[row, col], ...]}` coordinates, for example
     `{'table': [[3, 3]]}` for the answer "16,284".
     https://raw.githubusercontent.com/NExTplusplus/TAT-QA/master/dataset_tagop/tatqa_dataset_train.json
   - The README says these fields are generated by heuristic: "We heuristicly generate the 'facts' and 'mapping'
     fields". https://github.com/NExTplusplus/TAT-QA/blob/master/README.md
   - **HybridQA** stores answer nodes as `[text, [row, col], link, source]`. Because they were found by string
     tracing, the README warns: "the traced answer node is approximated, not guaranteed to be correct".
     Train example 0 traces one answer to four candidate nodes, including `'Kabul'` at both `[0, 2]` and
     `[5, 2]`. https://github.com/wenhuchen/HybridQA/blob/master/released_data/README.md ;
     https://raw.githubusercontent.com/wenhuchen/HybridQA/master/released_data/train.traced.json
   - **ToTTo** stores evidence as `highlighted_cells: List[[row_index, column_index]]`.
     https://github.com/google-research-datasets/ToTTo/blob/master/README.md
   - ToTTo's baseline attaches headers to a highlighted cell by using `column_span` to compute column offsets
     (`_add_adjusted_col_offsets`, `_get_heuristic_col_headers`).
     https://github.com/google-research/language/blob/master/language/totto/baseline_preprocessing/preprocess_utils.py
   - **TaPas** encodes structure as per-token row and column ids and selects answers by cell ("the average over
     logits of tokens in that cell"). https://ar5iv.labs.arxiv.org/html/2004.02349
   - **TabFact / Table-BERT** linearizes rows as templates ("row one's game is 51; the date is February; …")
     and keeps only the columns that hold entities linked to the statement (§3.2).
     https://ar5iv.labs.arxiv.org/html/1909.02164
   - **Table attribution work (TraceBack / CITEBench, 2026)** outputs `[(row_index, col_index), ...]` and scores
     attribution with precision and recall at row, column and cell level. https://arxiv.org/html/2602.13059
   - **Summary.** None of these systems checks evidence by matching a free-text span against linearized table
     text. Where text matching appears at all (HybridQA tracing, TAT-QA mapping), the authors present it as a
     noisy, weak-supervision heuristic.
2. **Known failure modes in the literature concern models reading linearized tables. None concerns a verifier
   that matches spans.**
   - LLM table understanding changes with "table input format, content order, role prompting, and partition
     marks" (Sui et al., WSDM 2024). https://arxiv.org/abs/2305.13062
   - FREB-TQA finds that state-of-the-art TQA systems "lack robustness" to changes in table structure,
     including row and column shuffling. https://arxiv.org/abs/2404.18585
   - Adversarial table permutation is a known attack on LLM table reasoning.
     https://arxiv.org/html/2605.00445v1
   - Linearization bugs can distort evaluation. FinQA's first `table_row_to_text` "causes label info leak and
     gives wrong results higher than actual ones for the retriever".
     https://github.com/czyssrs/FinQA/blob/main/README.md
   - Column misalignment is handled explicitly only when span metadata exists. ToTTo aligns headers with
     `column_span`, as described above.
   - I found no primary source on a *row-splice attack against quote-substring verification*. The closest
     mitigation pattern is FinQA's and FEVEROUS's: fix the evidence unit to a whole row or a coordinate-addressed
     cell, and attach its headers structurally.

## Repo facts

- `normalize_for_match` casefolds, applies NFKC and collapses whitespace. It keeps pipes, so a row break
  `|\n|` and an empty cell `| |` both normalize to `| |` (`numeric_utils.py:196`).
  - That is why a positionless "quote in source" test cannot tell them apart.
  - The raw slice that reopened the splice (`"$50,780 |\n| Intelligent Cloud |  |  |  |  |\n| R"`) is recorded
    in `docs/plans/2026-09-13-table-grounding-region-scoped-matching.md` (lines 67-80).
- `_quote_grounded_in_source` treats the table check as authoritative once any cell matches (`agent.py:1418-1420`).
  - Downstream, `value_not_in_quote` uses the loose 1% tolerance (`agent.py:1536-1540`).
- **The real motivating quote is on a table that the current code parses differently from the one the tests
  describe.** The transposed NVIDIA table is `chunks/NVDA/0001045810-26-000052_chunks.jsonl`, chunk_index 34.
  - Its rows are `Three Months Ended` / `Apr 26, 2026 | Apr 27, 2025 | $Change | %Change` / `($ in millions)` /
    `Compute & Networking` / `Graphics` / `Total`.
  - The model's quote is rejected in trace run `dabb3f85c8c7` in `trace_logs/traces.jsonl`. The quote is
    `"| Compute & Networking | $74,550 | … |\n| Graphics | 7,065 | … |"`.
  - `_classify_row` classifies `| Three Months Ended |  |  |  |  |` as a **label** (a group label). It is really
    a period header whose colspan was lost.
  - `_leading_header_context` stops at the first label or data row, so this table has **no header context at
    all**.
  - The `Apr 26, 2026 | …` and `($ in millions)` header rows after that label never enter any permitted region.
  - Measured: the permitted region of $74,550 is exactly
    `'| Three Months Ended |  |  |  |  |\n| Compute & Networking | $74,550 | $39,589 | $34,961 | 88% |'`.
- MSFT's year header `| 2026 | 2025 | 2026 | 2025 |  |` is shifted one column left of its data columns
  (`MSFT_SEGMENT_CHUNK` in `tests/test_table_grounding.py`). This colspan loss is the reason per-column mapping
  was removed.
- **Prototype.** I implemented and ran it in a scratchpad (`proto.py`, not in the repo). It compares the current
  `quote_is_grounded` with three candidate verbatim paths, each OR-ed with the current check:
  - **L0** is the proposal read literally. The verbatim occurrence covers the row label through the cell, the
    group label is always required when one exists, and there is no alignment constraint.
  - **L1** is L0 plus a start aligned to a row boundary and an end aligned to a cell boundary.
  - **R** is L1 with one change: the group label is required only when the matched span contains any label row.

## Inferences (mine, not from sources)

1. **Position is the missing ingredient, not verbatimness.** The 09-13 shortcut asked whether the quote exists
   somewhere in the source, and normalization erases the difference between a row break and an empty cell.
   Locating the occurrence in source offsets restores the row structure that normalization erased. This is the
   text-matching counterpart of the coordinate-addressed evidence that FEVEROUS, TAT-QA, HybridQA and ToTTo use.
2. **The literal proposal is not enough for the case that motivated it.** The group-label clause fails N1-N4
   because the transposed NVIDIA table's `Three Months Ended` row is classified as a group label. A correct
   quote of the three segment rows does not contain that label.
3. **Without alignment, the literal proposal reopens header cherry-pick (H2).** A verbatim span may start
   partway through a multi-cell header row, so it names "Nine Months" alone before a three-month value. The
   OR-ed path bypasses the existing cherry-pick check, so the new path needs its own defense.
   - Row-aligned starts close this structurally: any header row inside the span is then complete.
4. **"Group label if the span contains any label row" is sound**, given a contiguous span located in the
   source.
   - A span that reaches a *different* group's label *above* the own row must pass through the governing label,
     because it is contiguous.
   - A foreign label *below* the own row (S5) is the only way to put a misleading group name into a quote, and
     the rule rejects it.
   - A span with no label rows names no group at all. That matches today's accepted single-row
     `Revenue $34,681`.
5. Case by case against the test file:
   - **Splice (S1-S6, N6):** rejected. Either the span does not contain the own row from its label, or it starts
     mid-row, or it pairs the own row with a trailing foreign label and not its own.
   - **Cross-group steal (G1, `test_rejects_cross_segment_steal_via_a_near_tolerance_duplicate_cell`):**
     rejected, because the quote is not verbatim for either cell.
     - G2 is accepted by both the current and the proposed rule. It is not a new hole. It comes from the
       standing 1% tolerance in `locate_value` and `value_not_in_quote` (BACKLOG item at line 176).
   - **Wrong-period column:** a verbatim own-row prefix includes every earlier sibling value.
     - This is the same accepted tradeoff as `test_accepts_a_quote_naming_the_sibling_columns_value`.
     - The new path adds no period claim that the current path lacks.
   - **Header cherry-pick (H1, H4, AAPL test):** these are not verbatim, so the result is unchanged. The
     verbatim variant (H2) is closed only with row alignment.
6. A truncated trailing number (N7) is the reason to require a cell-aligned end: without it, a verbatim quote
   can carry a number that is not in the table.

## Open questions

- Should `_classify_row` treat a single-cell, unparenthesized row that sits *before any header or data row*
  (NVIDIA's `Three Months Ended`) as a header rather than a group label?
  - It would fix the NVIDIA permitted region for the current path as well.
  - It would also bring the dropped `Apr 26, 2026 | …` header row into the cherry-pick token sets.
  - It needs checking against every tracked table in which a real group label comes first. This is a separate
    change.
- Model quotes that include the prose caption before `<TABLE>`, or that drop pipes at row edges
  (`88%\nGraphics`), are not verbatim within the block. They fall back to the current path. How often does this
  happen in `trace_logs/traces.jsonl`?
- Should the verbatim path also require the claimed cell's own text to match the claim tightly? That would
  close G2, but it touches the 1% tolerance policy tracked in the BACKLOG.

## Recommendation

Add a verbatim, position-anchored acceptance path, OR-ed with the existing `quote_is_grounded` checks. For each
located cell, it accepts when **all** of these hold:

1. `normalize_for_match(quote)` (outer spaces stripped) occurs in the cell's own **table block**, normalized row
   by row and joined with single spaces, with per-row and per-cell offsets recorded.
   - Every occurrence is tried, because duplicate text is possible.
2. The occurrence **starts at a row boundary**: at the row's leading `|` or at its first cell's text.
3. The occurrence **ends at a cell boundary**: just after a cell's text, or just after the pipe that follows it.
4. The occurrence covers the claimed cell's row **from its first cell through the claimed cell**.
5. If the claimed cell has a governing group label **and the span contains any label row**, the span includes
   that governing label row.

Put it inside `table_grounding.py` as a helper, `_verbatim_row_span_grounded`, which needs the cell's
block/row/column position on `GroundedCell`. Do not put it in `agent.py`.
